# Web Cleaner

A browser userscript for a cleaner, ad-free, more focused web — built and verified against the live 2026 Facebook and YouTube DOM.

[Changelog](#changelog) · [Limits](#limits--what-it-cannot-do) — the version lives in the script's `@version` header, which is what your manager reads.

## Install

1. Install a userscript manager: **[Violentmonkey](https://violentmonkey.github.io/)** or **[Tampermonkey](https://www.tampermonkey.net/)** (Chrome/Edge/Firefox; on Android use Firefox + one of these, on iOS use the Userscripts app for Safari).
2. Click **[Install](https://raw.githubusercontent.com/pyxis3-ai/webcleaner/main/webcleaner.user.js)** — the manager will prompt you.
3. Updates are automatic: your manager re-fetches from the URL it was installed from. No re-pasting.

## One script, five modules

Each module runs inside its own error boundary, so one site's redesign breaking a module can't take down the others. Shared plumbing — the draggable button, storage, hotkeys, and the settings panel — is written once.

## Behaviour notes

- **Settings & auto-updates.** Every setting lives in the panel, so you never edit the script file and auto-updates keep working. Settings are stored under the `wc7_` prefix and survive version upgrades. Import/Export/Reset are in the panel's ⚙ section; imported files are type-checked and sanitised.
- **Settings are per-site on iOS.** Desktop managers expose `GM_setValue`, which is shared across every site, so a change made on one site applies everywhere. The iOS Userscripts extension implements the newer promise-based `GM.setValue` instead, and exposes it only to scripts injected in the content-script scope — which this script cannot use, because its YouTube ad blocking installs a getter over `ytInitialPlayerResponse` in the page scope. On iOS the script therefore falls back to `localStorage`, which browsers scope per origin. Practical effect: adding a host to the block list on one site does not block it from another, so configure the Blocker on the site you want blocked.
- **Focus Pack is opt-in.** `Focus` and `Schedule` are both **OFF by default** — nothing in the Focus Pack is blocked until you turn one on. Two independent switches feed the same filter (`Focus` blocks always, `Schedule` only inside its window), so the Blocker section shows a live **effective state** line: `● Focus pack BLOCKING NOW (inside schedule 09:00–18:00)` or `○ Focus pack not blocking (outside schedule …)`, and flags when the site you are on is one of them. **Upgrading keeps your saved settings** — if `Schedule` was on it stays on, and the state line now makes that visible.
- **Degradation is visible, not silent.** If Facebook or YouTube rotate their markup and filtering stops matching, the panel shows a warning line and the affected module's button gets an amber ring. The check is precise: if hiding is working, no sponsored label is ever visible, so any visible one is a genuine miss. It never guesses at hiding things.
- **Widen feed.** Hiding both sidebars reclaims roughly half a desktop window, so the feed widens to fill it (default 1100px; tune under Facebook → Advanced → **Feed max width**, or switch **Widen feed** off for Facebook's native 680px). Wider columns letterbox tall images — lower the value if you scroll a lot of portrait media.
- **Hide feed.** `Hide feed` (Facebook and LinkedIn, **OFF by default**) removes the feed column itself rather than filtering what is in it, for when you want the rest of the site — Messenger, groups, profiles, notifications, search — without the scroll. It is scoped to the home feed only (`/` and `/home.php` on Facebook, `/feed` on LinkedIn), so every other page is unaffected, and it stacks with the sidebar, composer and top-bar switches if you want the page empty. It hides the feed and nothing else — search, the tab strip and the global nav stay where they are, on desktop and on a phone. Nothing is deleted — like every other switch it hides by stylesheet, so turning it back off restores the feed. If feed detection fails the module falls back to normal filtering rather than blanking the page.
- **Distraction-free watch page.** `Related`, `Comments`, `Chips`, `Merch/promos` and `Live chat` each hide that part of the YouTube watch page. `Related` is ON by default; with `Widen player` the video expands into the reclaimed space (measured 996×560 → 1385×779 at 1440px).
- **Facebook mobile.** A logged-in phone is served the responsive `www.facebook.com`, _not_ `m.facebook.com`, so the module picks its code path by inspecting the markup rather than the hostname. If something slips through, add markers under **Extra junk phrases**.
- **Site Blocker** needs Tampermonkey or Violentmonkey (GM storage + menu). The snooze applies to every filter, adult included. For comprehensive adult blocking across all browsers and apps, pair it with a DNS family filter (Cloudflare `1.1.1.3` or NextDNS) — a userscript can't enumerate the whole category.
- **YouTube detection is measured, not guessed.** Both of YouTube's bundles were pulled and read: the player (`base.js`) and the 10.8 MB desktop app bundle. They share a registry of **25 named detection signals** — `DI7` in the player, `naM` on desktop, same names, same two-bit slots in a `CATSTAT` register that is XORed with a BotGuard value and sent on the attestation ping as `r6b`, beside `r6a` carrying the `DCLKSTAT` bait result. The player implements four; the desktop bundle implements the rest, including a JSON canary, a `Response.json` canary, a spoofed-URL `fetch` honeypot, a honeypot skip button, bait elements built from an obfuscated string table, and a `<script>`-body scanner whose signature list is server-updatable. The module is built around what they actually check — see the 8.22.0 changelog for the signal-by-signal account. Note also that full uBlock Origin has been disabled on stable Chrome since v138 and its store listing was removed on 31 August 2026, so a Chrome + uBlock pairing has ended; desktop Firefox remains the capable option. For network-level blocking, pair with uBlock Origin — though note it trips two signals this script does not: `DCLKSTAT=3` when it blocks the `static.doubleclick.net/instream/ad_status.js` bait, and the resource-timing probe that fetches a server-supplied test URL and compares it against a control. YouTube deliberately serves playback errors ("Something went wrong. Refresh or try again later.") to users it detects as ad-blocking. Toggling **Anti-AB** off will show you YouTube's real message.

## Limits — what it cannot do

- **Server-side ad stitching.** YouTube bakes some ads into the video stream itself. No client-side script can remove those.
- **Being detected at all.** Nothing here stops the _reporting_. `onAbnormalityDetected` sets the `d.p_` register to detected before any of this module's handling runs, and every signal also emits a `biscottiBasedDetection` event independently of what the page does afterwards. What the module can do is avoid tripping signals in the first place, and disarm the enforcement that follows one. Those are different things, and only the first is prevention.
- **Skipping an ad that does play.** Every route out of a playing ad is instrumented. A scripted click on the skip button is scored as detected and then refused, so it cannot work; a seek is reported unconditionally. If an ad reaches the player, the honest options are to wait it out or to click skip yourself. This is why removing the payload before the player sees it is the only mechanism the module relies on, and why `Seek past ads` ships off.
- **In-video sponsor segments.** Creator read-outs ("this video is sponsored by…") are not ads in the DOM sense; use SponsorBlock for those.
- **User-Agent headers.** No userscript can change a navigation's request headers. Sites that pick their interface server-side from the UA (and redirect before any page JS runs) still serve their desktop interface. `Reflow CSS` then restyles what was served, which is what makes Mobile mode work on desktop; it cannot fetch a different page.
- **Cross-origin stylesheets that block CSSOM reads.** `Reflow CSS` rewrites `@media` rules in place, which needs `cssRules` access. Nearly all sites allow it (measured: Wikipedia 17/17 sheets readable, BBC 6/6, YouTube 15/18 — the 3 blocked are Google Fonts with no layout rules). LinkedIn is the known exception: its main sheet is CORS-blocked, so Mobile mode on desktop reflows little there.
- **Per-site overflow at phone width.** The frame clamps the page and contains `position:fixed` overlays, but a site's own component can still overflow its container if that component has no mobile styling of its own (BBC's cookie banner buttons, for example). Cosmetic, and confined to the element.
- **Sandboxes that share page objects through Xray wrappers.** Tampermonkey's `JavaScript` sandbox on Firefox, and Violentmonkey's content mode after a CSP fallback, hand the script a wrapped page window whose objects can only be modified with `exportFunction`/`cloneInto`, which this script does not use. There the YouTube payload hooks and the View Mode signal spoof do not reach the page; DOM hiding, the blocker and the panel are unaffected. Chrome, Tampermonkey's default `raw` sandbox, Violentmonkey's page mode and the iOS Userscripts app run the script in the page itself.
- **Substring matching.** Facebook splits the "Sponsored" label across text nodes, so detection must use substring matching — which means text containing "sponsored" as a substring (e.g. "unsponsored") can be hidden. Exact matching was tested and caught 0 of 2 real ads, so this trade is deliberate.
- **Opaque `l.php` redirects.** `Strip tracking` unwraps `l.facebook.com/l.php?u=<encoded URL>` back to its destination, and that still works where Facebook encodes one. Facebook now issues some of these with an opaque token instead (`?u=AUC4PGjAr9mDl69…`), which carries no recoverable URL, so those links are left as they are rather than mangled. Measured on a live feed: 6 `l.php` links present, 5 unwrapped, 1 opaque. `utm_*` parameters, `ping` attributes and `data-lynx-uri` are stripped in every case.
- **Schedule day-spill.** A schedule of `Mon` `22:00–06:00` does not block Tuesday 02:00.
- **Markup rotation.** Meta and Google change markup without notice. Three things happen: the panel warns you, the module button gets an amber ring, and a rendered-text fallback engages that recovers some ads without depending on markup. Recovery is partial by design — the fallback is bounded and hides only the tightest element containing a visible sponsored label, so it never risks the page. Full coverage returns when selectors are updated.

## Changelog

### 8.23.0

A full audit: the script, the three managers' published source, the live YouTube endpoints and the neighbouring scripts, with a committed test suite. Every claim below is measured in a browser or quoted from a manager's code.

- **YouTube ads played on every video after the first.** Measured on a live watch page (12 October 2026): clicking a related video fetches `/youtubei/v1/get_watch`, a 1.1 MB response carrying `adPlacements`, `adSlots` and `playerAds`. It is a two-element _array_ (`[{playerResponse}, {watchNextResponse}]`) that the page consumes as a stream, so it never reaches `Response.json()`, where 8.22.0 did its pruning. Three independent misses: the endpoint was not in the gate, the scrub skipped arrays, and the hook was on a method the page does not call. The response body is now rewritten inside a `fetch` wrapper — the way uBlock Origin's `replace-fetch-response` does it — keyed on the URL the network served (`Response.url`), so the synthetic-`Response` canary and the `data:`-URL honeypot pass through untouched exactly as before, and the replacement carries the original `url`, `ok`, `redirected` and `type`. Shorts had the same gap: the live endpoint is `/youtubei/v1/reel/reel_watch_sequence`, not `/youtubei/v1/reel_watch_sequence`. Every `/youtubei/` response is now in scope on both transports. Measured after the change on the same navigation: the second video's player response carries no `adSlots` or `playerAds`, `getPresentingPlayerType()` reads 1 where it read 2 before, and the page's `fetch` still reports `[native code]`, name `fetch`, length 1. The 8.22.0 suite had verified both transports by calling `.json()` itself, which is not what the page does.
- **`@grant unsafeWindow` is declared.** 8.20.0 moved the YouTube hooks onto `unsafeWindow` without granting it, on the belief that sandboxing managers expose it regardless and that granting it would push the iOS host into the content-script scope. Both halves were checked against source. Violentmonkey does expose it unconditionally (`gm.unsafeWindow = global` in its API wrapper, for any `@grant` other than `none`), but Tampermonkey's documentation says `@grant` "is used to whitelist `GM_*` and `GM.*` functions, the `unsafeWindow` object and some powerful `window` functions", so under its sandbox the hooks fell back to the sandbox's own `window` and never reached the page. The iOS Userscripts app filters `@grant` values against a fixed list (`validGrants` in `Functions.swift`) that contains neither `unsafeWindow` nor the legacy `GM_*` names already in the header, so the grant changes nothing there. The View Mode spoof now targets the same page window, which it never did.
- **Facebook ads are removed from the feed responses, not only from the DOM — verified on the live logged-in feed (12 October 2026).** With the new `Block ad data` switch on, the page received its `/api/graphql/` feed responses carrying **0** `SponsoredData` objects where the raw network response held 6, the feed's scroll height collapsed from roughly 18,000px to 2,000px, and the two visible sponsored-info links dropped to zero. uBlock Origin stopped relying on markup for Facebook; its maintained filters edit the `/api/graphql/` responses, which arrive as JSON lines. The edits here are translated from its `jsonl-edit-xhr-response`/`json-edit` rules with the JSONPath semantics read from source: a feed edge whose `category` is `SPONSORED` loses its `node`, and any `node` or `nodes[]` entry carrying a descendant with `__typename: "SponsoredData"` is dropped. Matching is on the typename, not the key, because the live sponsored node carries that child as `th_dat_spo`, not `sponsored_data`. The responses are consumed as a stream from `readyState` 3, so the `XMLHttpRequest` replacement is a subclass whose `response`/`responseText` getters re-edit on every read; the subclass is registered as the native for `toString`. **`JSON.parse` is deliberately left unhooked**: Facebook parses a canary of this exact shape (`{"data":{"node":{"s":{"__typename":"SponsoredData"}}}…}`) through it inside a throwaway frame, and when the canary comes back edited it falls back to its own JSON5 parser, so a parse hook is both reported and bypassed. Facebook also fetches clean natives from that frame to get around the `fetch` and XHR hooks — uBlock counters this with `trusted-prevent-dom-bypass` — so every frame reached through the `contentWindow` or `contentDocument` getter has the parent's `fetch`, `XMLHttpRequest` and `Function.prototype.toString` copied in, and `toString` on the patched natives reports the native string. A desktop DOM rule covers the ads that survive the response edit on some sessions: the label there is drawn as an SVG with no text, identifiable by its sponsored-info link (a query-only `href` with `__cft__` and no `__tn__`), so that story is hidden too. On by default. The response edit and frame guard were confirmed live; the DOM rules remain fixture-verified, since the live markup rotates.
- **The YouTube and Facebook network layers are one.** `hookResponses` (fetch and XHR, gated on the served URL), `textEditor` (JSON or JSON-lines), `maskNatives` and `guardFrames` serve both modules; YouTube also guards frames now, since uBlock's filters show YouTube using the same clean-frame trick for `fetch`.
- **Facebook hid any post whose header mentioned stories or reels.** The exact-label set used for whole-token matching had been built from the ad labels _plus_ the tray titles (`Reels`, `Stories`), so a header such as `Check my stories` matched the token `stories` and the post went, on desktop and mobile. The token set is now the ad labels only; tray titles are still matched as a whole element's text. Pinned on both shells.
- **Facebook's tile-grid pass read hidden text.** It matched on `textContent`, so a hidden `Sponsored` honeypot inside a listing hid the listing — the trick 8.4.0 made the rescue path immune to. The pass now uses the same rendered-text tightest-match as the rescue and LinkedIn, and remembers a clean verdict after six passes like every other pass. Pinned: a tile with a `display:none` label is kept, the visibly labelled tiles are hidden, the row is not.
- **LinkedIn matched the whole post, not its header.** `promoted` anywhere in a post's rendered text hid it ("happy to share that I've been promoted"), and the German marker `anzeige` is a substring of `Mehr anzeigen`, the see-more control on every long German post. Matching is now restricted to the top 130px of the candidate, the header band Facebook already uses, and `Anzeige`/`Ad`-style labels are matched as whole tokens there. Fixture-verified only; the live LinkedIn feed was not re-checked in this pass.
- **The panel is built from DOM nodes.** Measured in Chromium under `require-trusted-types-for 'script'` with the script's policy name disallowed: `innerHTML` throws and so does `DOMParser.parseFromString`, so the 8.2.0 fallback never had a path to work and the panel always degraded to a notice there. Elements are now created directly, which needs no Trusted Types policy at all, so the panel renders on every site; the policy, the HTML escaper and the degraded notice are gone. Pinned under an enforced policy.
- **One module runner.** Facebook, YouTube and LinkedIn each wired their own observer, intervals, scroll listener, hotkey, health ring and enabled gate, and disagreed in the details — YouTube's feed tagging and nudges ignored the off switch, Facebook's video muting kept running with the module off, LinkedIn had no rescue path. `runModule` now owns all of it; a module supplies its stylesheet, its sweep, and optionally a per-frame hook and a rescue vocabulary. The three sponsored-label lists are one, and the two zero-width-character patterns are one.
- **`history.pushState` is no longer patched.** Navigation is detected by comparing `location.href` on each tick, which needs no page-visible modification and works in sandboxed worlds, where a patched `history` on the sandbox's window never saw the page's calls. The watch-page marker, the autoplay nudge and Facebook's per-route state all run from it; pinned.
- **Document-start before `<html>` exists is handled once.** 8.8.0 fixed `initVM` for a manager that runs document-start before the root element exists, but every other module appended its stylesheet unguarded and died the same way, and the blocker's screen waited for its 5-second retry. A single `onRoot` defers DOM work until the root exists; the test harness injects at that earlier moment deliberately, and the block screen now attaches the button cluster itself, since `DOMContentLoaded` does not fire after `window.stop()`.
- **Mobile `Top bar` now applies with `Hide feed` on**, as it already did on desktop.
- **Smaller things.** The panel showed `v8.21.0` on 8.22.0; the constant is now pinned to the header by a test. Settings were written twice on managers that provide both GM APIs, and mirrored to `localStorage` where nothing read it. `Includes paid promotion` was in the rescue vocabulary, which is a creator disclosure, not an ad. The long YouTube comments duplicated the 8.22.0 changelog; the code keeps six one-line notes at the places that must not be "fixed". `.prettierignore` carried entries for files the repository does not have.
- **A desktop sponsored-info-link rule.** Some sessions serve the sponsored story with its label drawn as a textless SVG, so no text match reaches it; it is identified by its sponsored-info link — a query-only `href` carrying `__cft__` without the `__tn__` an organic timestamp link has — and the story is hidden. Pinned by a fixture whose timestamp link is kept.
- **Tests.** `test/` holds the Playwright suite described under Verification. Against 8.22.0 it fails on exactly the defects above. The Facebook response edit, the clean-frame guard and the `JSON.parse` pass-through were additionally confirmed on the live logged-in feed.

### 8.22.0

Reverse-engineered YouTube's live anti-adblock and rebuilt the module around it. Both bundles were pulled and read — the player (`base.js` `e937390a`, 2.6 MB) and the desktop app (`ytmainappweb`, 10.8 MB). Every claim below is quoted from that code or measured in a browser against it.

**What YouTube runs.** A registry of 25 signals — `DI7` in the player, `naM` on desktop, identical names and slots. Fourteen own two bits each in a `CATSTAT` register; `CATSTAT` is XORed with a BotGuard value and reported on the attestation ping as `r6b=broadSpectrumDetectionResult`, next to `r6a=reportingStatus` carrying `DCLKSTAT`. Every signal also emits a `biscottiBasedDetection` client event (id 439), and `CATSTAT` rides along on user-feedback reports too. The result codes are `0 = DETECTED`, 1 not detected, 2 unspecified, 3/4 failure; only 0 sets the enforcement flag.

**The signals this module was tripping, and what changed:**

- **`i.s_` / `ISDSTAT` (bit 8) — the skip button.** Both skip-button classes route `onClick` through `lc5(event)`, which scores `isTrusted === false` as detected, raises `onAbnormalityDetected`, and takes the branch that _skips the skip_: `super.onClick()` only runs in the `else`. A scripted click was reported and refused — it never skipped an ad. It fired every 400 ms for the length of every ad, twice per attempt, because `tap()` dispatched both `el.click()` and a synthetic `MouseEvent`. **Clicking is gone; `tap()` is deleted.**
- **`i.f_` — a honeypot skip button.** `XBe()` appends an invisible `<button class="ytp-ad-skip-button">` with zero size and `opacity:0`, waits 50 ms, and reports detected if anything clicks it. Removing the auto-click closes this too.
- **`a.s_` / `ASDSTAT` — seeking inside an ad.** `sHY()` runs on any `seeking` event while `videoData.isAd()`, and its verdict is the literal `xV(0, "a.s_", …)`, hard-coded to detected. `isTrusted` only decorates the reported states — measured in a browser, a programmatic `currentTime` assignment produces a `seeking` event with `isTrusted === true` and is reported all the same. There is nothing to evade: the seek _is_ the signal. **`Seek past ads` now ships off**, relabelled `Seek past ads ⚠`.
- **`n.k_` / `NKDSTAT` (bit 20) — time compression.** Every 5 s of ad media time, `let r = M < G*.4 ? 0 : 1` flags an ad whose media time outruns the wall clock by more than 2.5×, and calls `onAbnormalityDetected` directly on pre-rolls. Seeking to `duration - 0.1` trips it; so does any playback-rate trick.
- **`m.p_` / `MBSTAT` (bit 28) — the server/client cross-check.** `msy(playerResponse)` is true when a placement of kind `AD_PLACEMENT_KIND_START` exists or a slot triggers on `SLOT_TRIGGER_EVENT_BEFORE_CONTENT`; when a SABR context update of type 5 arrives and `msy()` is false, the player reports and raises `onAbnormalityDetected`. Deleting `adPlacements` outright is what announced the prune. A live fetch of a watch page with no ad to serve carries exactly one placement — a `clientForecastingAdRenderer` at `KIND_START` — so **the pre-roll slot is now left standing and only the renderers that would play something are dropped.**
- **`j.s_` (bit 2) — the `JSON.parse` canary.** This is the one that mattered most. A canary JSON string _and the object it must parse to_ are baked into the desktop bundle; `_.RhU()` runs `JSON.parse` over the canary and deep-compares. The canary contains `adPlacements`, `adSlots` and `playerAds`, so **any** `JSON.parse` hook that prunes ad keys fails it. **The `JSON.parse` hook is removed entirely** — nothing here patches it any more.
- **`_.QeL` — the same canary through `new Response(str).json()`.** A synthetic `Response` has `url === ""`; a real one does not. The `Response.prototype.json` hook now acts only on a URL that came off the network, so the canary passes through untouched.
- **`NMP` — a spoofed-URL `fetch` honeypot.** It builds a `data:` URL `Request` and overrides its `url`, `method`, `mode` and `bodyUsed` getters to claim it is `POST /youtubei/v1/player`. Any blocker keyed on the _request_ URL rewrites the canary and is caught. Measured: `Request.url` reports the player endpoint while `Response.url` reports the real `data:` URL — so **every interception here keys off the URL the network actually served, never one the page hands us.**
- **`e.h_` (bit 6) — bait elements.** `GDv` is a table of base64 strings decoded by `_.Vs()` — base64, rotate by `-68 mod len`, truncate at `#`. Decoded, it builds a nested chain of decoy divs (`id="primary"` → `class="ytd-two-column-browse-results-renderer style-scope"` → `id="masthead-ad"` → … → `class="ytd-ad-slot-renderer"`) plus a bare `<div id="player-ads">`, appends them to `<body>`, and scores `getComputedStyle(innermost).display === "none"` as detected. Measured against the old stylesheet: the chain ending in a _class_ was safe, because the module matches `ytd-ad-slot-renderer` as a tag; the bare `<div id="player-ads">` matched the unscoped `#player-ads` rule and tripped it. **`#player-ads` and `#masthead-ad` are now scoped to the app root**, which the bait sits outside of.
- **`p.h_` (bit 12) — the enforcement popup, now clean rather than merely tidier.** `o49()` scores a `ytd-enforcement-message-view-model` that is absent _or_ computes to `display:none` as detected — and it runs only from `xUU()`, immediately after `n0r()` has opened the popup, so it never fires unless enforcement has already started. Better: **both** enforcement paths are gated on `U2L(playerResponse)`, which reads `auxiliaryUi.messageRenderers.bkaEnforcementMessageViewModel`. The `onAbnormalityDetected` handler only calls `stopVideo()` and rewrites `playabilityStatus` to `{status:"ERROR", errorScreen:{enforcementMessageViewModel}}` _`if (S = U2L(f))`_, and the popup path only reaches `n0r()` when that renderer exists. So dropping it from the payload disarms the enforcement itself — the video is not stopped, the playability status is not rewritten, the popup never opens, and `o49()` is therefore never called. `errorScreen.enforcementMessageViewModel` is dropped too. And if a dialog is delivered by some other route anyway, the node is now **left in the DOM and explicitly kept at `display:block`**, hidden instead by `visibility`, `opacity` and off-screen positioning, with only the dialog shell and backdrop removed — so `o49()` reads clean. The previous build deleted the node, which is precisely what the signal scores.
- **`s.i_` (bit 14) — a `<script>` body scanner.** `_.gaY()` walks every `<script>` element and matches `textContent` against signatures from the `ab_det_sc_inj_val` experiment flag, defaulting to `json=JSON.parse(text);for(k of["playerAds","adPlacements","adSlots"])`. The list is server-updatable. Dropping the `JSON.parse` hook removes the resemblance.
- **`o.p_`, `o.a_`, `g.o_`, `a.o_`** — integrity checks on `Object.prototype` (against a decoded watchlist of `globalCallbacks`, `onAbnormalityDetected`, `onAdSkip`, `raw_player_response`, `adSlots`), on `Array.prototype.push`/`forEach`/`filter`, on `btoa`, and a `for…in` vs `Object.getOwnPropertyNames` comparison over the player response. This module trips none of them.
- **`DCLKSTAT` and the resource-timing probe** — `static.doubleclick.net/instream/ad_status.js` is loaded as bait (`1` = loaded and `google_ad_status` set, `2` = loaded without it, `3` = never loaded in 5 s), and a second probe fetches a server-supplied test URL against a control and compares Resource Timing entries. Both catch network-level blockers. This module blocks no requests and reads clean on both; pairing it with uBlock Origin does not.

**Other changes:**

- **The page marker is gone.** `window.__wcAdPruned` was a uniquely named global that identified the script to anything enumerating `window`.
- **The three native patches are now Proxies, and match their natives completely.** Measured in a browser: a `Proxy` over a native function forwards `name`, `length` and the absence of `.prototype`, reports the target's own-property list, and — the part that matters — `Function.prototype.toString` on it returns `"function () { [native code] }"`. So the whole passive shape matches **without** patching `Function.prototype.toString` globally, which is what uBlock's `proxyApplyFn` has to do only because it chains many proxies through one shared `toString`. The alternative of hanging an own `toString` on a shim was rejected by measurement: it leaves own properties `[length, name, prototype, toString]` where a native has `[length, name]`. Worth stating plainly, though: **neither bundle runs a `toString` integrity check for ad-block detection.** The six `[native code]` tests in the desktop bundle are Zone.js, Closure and gapi polyfill probes over `Node`, `Element`, `ShadowRoot` and `MutationObserver` — and `XMLHttpRequest` and `Response` appear in neither of those lists, so the patches here are outside that path entirely. This is shape hygiene against a check that does not currently exist, bought at no cost.
- **A real XHR path.** The player response is rewritten on `XMLHttpRequest` as well as `fetch`. The URL is captured inside the `open()` wrapper, before the page can touch the instance; `responseURL` is consulted only as a veto, because it is an accessor a page can redefine on its own object — the same trick `NMP` plays on `Request`. A first cut gated on `/^https?:/` against the raw `open()` argument and silently did nothing, because YouTube requests these paths relatively; the URL is resolved against `location.href` first.
- **The scrub no longer walks every parsed object,** and is capped at depth 8. It previously ran over the result of every `JSON.parse` on the page to depth 14 and could delete an `adSlots` key out of an unrelated payload.
- **Verified by executing the module, not by reading it.** The suite loads the real `webcleaner.user.js` in a page with only the host constant swapped, runs it, and then puts YouTube's own predicates — transcribed from the two bundles — against the resulting page: 33 checks covering `j.s_`, `_.QeL`, `NMP`, `e.h_`, `p.h_`, `o.p_`, `o.a_`, `a.o_`, `g.o_`, `fg6`, `s.i_`, `i.f_` and `m.p_`, the passive shape of all three patched natives, and — the part that matters — that ads are still stripped from a genuine response on both the `fetch` and XHR transports. All 33 read as intended.
- **That suite exists because the previous one gave a false pass.** An earlier version read the selector strings out of the file textually instead of running the module, and so did not notice that a comment inserted with literal `\n` escapes had folded onto one line and swallowed the `ban:` property whole — `SEL.ban` was `undefined` and the ad stylesheet was never built. `node --check` passed, prettier passed, and the old `e.h_` check passed too, because with no stylesheet at all nothing gets hidden and the bait looks clean. Re-running the current suite against a deliberately re-broken copy fails it on `yt-css stylesheet injected` and `ban selectors present`, which is the negative control the old one lacked. The XHR relative-URL bug was caught the same way.

**The full detector set, exercised.** The master sweep was recovered — `Q1f()` in the desktop bundle runs sixteen checks in a fixed order, and the player runs four more, so nineteen of the twenty-five registry slots are actually implemented; the rest are declared with no body. Reading `Q1f` turned up three checks the earlier pass had missed, and one correction:

- **The bait table used at runtime is `okI`, not `GDv`.** They decode to the same element names but carry different random salts, and `okI` has a third chain the other lacks: a bare `<ytlr-banner-cta-renderer>`, created by _tag name_. That matters because the earlier conclusion — "tag selectors are safe, id selectors are not" — only held for the table being read. `ytlr-` is the living-room prefix and this module matches only `ytd-`, `ytm-` and `ytmusic-`, so it stays clean, but the general rule was wrong.

- **One text reader instead of two.** `readText` and `visText` were the same tree walk, the same visibility filtering, the same de-duplication by rendered position and the same sort, differing only in that one accepted a vertical band and the two returned differently-normalised strings. They are now a single `visText(scope, cap, bandTop, bandBottom)` where the band is optional, and every caller normalises, which is what most of them already did.
- **One tightest-match search instead of two.** The health rescue sweep and the LinkedIn sweep both implemented "hide the smallest element whose visible text matches a marker, unless a child matches too" — the same knowledge, written twice with different geometry limits. Extracted as `tightestMatch(el, marks, fits)`, with each caller passing its own `fits`. Copy-paste detection now reports **0 clones** at a 5-line threshold.
- **The view-mode switcher had a fourth private debounce**, using `requestAnimationFrame || setTimeout`, plus an ad-hoc `__wcVpObs` flag stashed on a DOM node. Both are gone; it uses the shared helper and a local variable.
- README corrected where it had drifted: the Facebook row did not mention Follow suggestions or empty-card collapsing, and both it and the settings note claimed everything is deleted and stored in the manager's storage, neither of which is true after 8.12.0 or on iOS.

### 8.12.2

- **One scheduler, one toggle, one way to switch a module off.** The three modules each carried their own idle-debounce wrapper, and they disagreed — two used `requestIdleCallback`, LinkedIn used a raw `requestAnimationFrame`, and only one contained its errors. There is now a single `debounced` helper, and its idle callback is bounded by a 250ms timeout so a busy page cannot defer a sweep indefinitely. Every module already has an interval backstop, so this is latency, not correctness.
- The three toggle functions were the same four steps written three times, and they disabled their module two different ways: Facebook and LinkedIn gated every CSS rule behind a root class (`.fcf-off`, `.li-off`) while YouTube set `disabled` on its stylesheet. Since each module's rules live in a single `<style>` element, the stylesheet flag does everything the root class did with one fewer concept. Both classes and every `html:not(.…-off)` prefix are gone, replaced by a `MODULES` descriptor and one `toggleModule`.

### 8.12.1

Pinned by a test asserting a sponsored reel advances exactly one screen and a genuine one does not move.
- Pinned `prettier` to an exact version — `latest` meant every install pulled whatever was newest, which is neither reproducible nor safe against a compromised release, the same concern that removed the `npx@latest` fetch from the pre-commit hook.

### 8.12.0

- **One pipeline for feed filtering, replacing four overlapping ones.** The Facebook module had accumulated three ways to hide something (a `data-fcf` attribute, a separate `data-fcf-e` attribute, and `dropPost` calling `.remove()`), four per-node state fields (`_wc`, `_wcN`, `_wcE`, `_wcSig`), two "is this element empty" predicates that disagreed, and two post enumerations. Each had been correct in isolation and wrong together. There is now a single path: enumerate slots, classify once, hide reversibly, anchor the scroll.
- **Nothing is removed from the DOM any more.** `.remove()` existed because hiding a post left its blank space behind — but the space belonged to the post's fixed-height wrapper, not the post, so hiding the wrapper collapses it completely. `slotOf` walks up through single-child parents to that wrapper. This is why the destructive behaviour was never necessary, and it removes a whole bug class: hiding is undone by the module's off switch, so turning Facebook off now genuinely restores every post. Pinned by tests asserting the junk post is invisible, still present in the DOM, and leaves **0px** of blank.
- **One scroll anchor for both scroll hosts.** `keepScrollAnchored` only ever called `scrollBy`, so it could not compensate the Reels inner scroller, which needed its own `scrollTop` arithmetic. It now resolves the scroll host — the Reels scroller or the document — and anchors either.
- **One node-state store shared by every module.** LinkedIn had its own `_li`/`_lisig` copy of the same idea; both now use a single `WeakMap` and one `fresh()` helper that resets a node's verdict when its content changes.
- `processMobile`'s slot scan is now gated on the mobile shell, so it cannot touch a desktop page. Verified: 0 spurious changes across eight unrelated sites, and the full harness set is unchanged.

### 8.11.5

- **Settings use the modern `GM.*` storage API when a manager provides it, instead of only the legacy `GM_*` one.** `gSet` now mirrors writes to `GM.setValue` as well as `GM_setValue` and `localStorage`, and `hydrateShared` seeds `localStorage` from `GM.getValue` at startup so the next page load starts in sync. - **Verified mobile Shorts structurally.** `#shorts-player` does not exist on mobile — the player is `#movie_player`, so the existing fallback is load-bearing — and no false skip occurred on a normal Short after the fix.

### 8.9.0

- **New: `Follow suggestions`.** Verified against a live logged-in feed, Facebook no longer labels its recommended posts "Suggested for you" — across a full scroll of that feed the phrase appeared **zero** times. What it does instead is put a bare **Follow** button after the author, giving headers like `Proton · Follow · 7h` and `Turn key narrowboats · Follow · 7h`. No phrase list could catch that, and substring-matching "follow" would be reckless because it also matches _followers_, _following_ and any post that merely says "follow me". Detection is therefore element-level: an innermost clickable element inside the post's 130px header band whose visible text is exactly "Follow". Measured live: 8 distinct posts flagged against 57 distinct posts kept, with **no false positives** — the composer, friends' posts, group posts and sponsored posts were all left alone, and no post whose header merely contained the word "follow" was flagged. On by default, switchable in the panel, and localized for the common variants.
- **On the 8.8.1 matcher change, measured properly.** An earlier note here claimed the old mobile matcher caught "0 of 76" posts. That figure came from feeding _desktop_ concatenated headers into both matchers and does not describe the mobile path, which is corrected now. `processDesktop` reads one concatenated header band, so with labels trailing the page name — `Haven House Children's Hospice · Sponsored`, `The Queens · Sponsored` — `startsWith` genuinely could never fire there, and `includes` is required. `processMobile` instead tests individual elements under 40 characters, where a span reading exactly "Sponsored" already matched. Re-measured on a live logged-in mobile feed: across 46 posts the old and new matchers both hid 17. The change is still correct — it aligns the two paths and catches elements combining author and label — but it is a robustness fix on mobile, not a repair of a total failure.
- **Confirmed the LinkedIn limitation.** On a live logged-in feed, 1 of 5 stylesheets is CORS-blocked and the readable ones carry **zero** width-based media queries, so `Reflow CSS` genuinely has almost nothing to rewrite there. Promoted/Suggested detection itself works: 8 of 23 scanned posts matched.

### 8.8.2

- **Fixed: ad skipping never ran on mobile.** Mobile YouTube loads a different player binary — `player-plasma-es6` rather than desktop's `player_ias`. Of the eight `.ytp-ad-*` overlay classes the ad-UI test looked for, **all eight are absent** from the mobile player, so `adUiPresent` stayed false there. The gate was `(adClass || adApi) && adUiPresent`, so on mobile it could only fire once a skip button had already rendered — the unskippable opening seconds were never detected, `Mute ads` never engaged, and unskippable ads were never seeked past. Detection now trusts `getPresentingPlayerType()` on its own, present 47 times in the mobile player and returning 1 for ordinary playback on both platforms; the older class path keeps its UI confirmation. The same one-sided gate is fixed for Shorts. (An earlier draft of this note also claimed `ad-showing`/`ad-interrupting` never appear on mobile. Those strings are absent from the mobile _binary_, but the classes are applied to the player at runtime — a captured live mobile ad shows `cls: true`. The half that actually failed was the ad-UI test, not the class test.)
- **Guarded `Seek past ads` against real videos.** Now that an API reading alone can trigger a skip, the seek additionally requires a duration of 180s or less, so a misread can never fast-forward a genuine video. Verified on live playback: `getPresentingPlayerType()` reports 1, the video is left unmuted and unseeked on both desktop and mobile.
- **Throttled the skip tap.** `tap()` fired on every DOM mutation during an ad — 126 synthetic tap sequences in 2.6 seconds on desktop. Now capped at one per 400ms, which cut it to 10 while still skipping and muting.
- **Mobile ad-UI selectors added** for the two that do exist in the mobile player, `ytp-ad-progress` and `ytp-ad-skip-button-container`.

Validated on live pages: normal playback untouched and a simulated ad muted and skipped, on desktop and mobile, over repeated runs. Mobile Shorts could not be confirmed end to end — signed-out Shorts redirects to a consent page — so that path is fixed structurally from the player source but is unverified against a live Short.

### 8.8.1

- **Fixed: mobile YouTube loaded forever on search and feed pages.** `Related` (on by default) injected `ytm-single-column-watch-next-results-renderer` and `ytm-item-section-renderer:has(ytm-video-with-context-renderer)` as global CSS. On desktop the equivalent selectors exist only on the watch page, so it was self-scoping; on mobile `ytm-item-section-renderer` is the generic feed section, so it also hid search results, and any feed built from it. Measured on a live mobile search: one matched element wrapped all 18 results (3.5M px², 3099 of the page's 5267 text characters). Because that container was `display:none` the document never grew past 915px, so YouTube's infinite scroll kept requesting continuations to fill a viewport that could never fill — 117 result nodes loaded instead of 19, every one of them invisible. That runaway is what "keeps loading" was. The mobile watch-next rules are now scoped to `html[data-yt-watch]`, set from `location.pathname` and refreshed on SPA navigation. Verified: search shows 19 of 19 results with no continuation loop, watch-page related videos still hidden, and the marker toggles correctly across pushState navigation both ways.
- **Fixed: Facebook suggested posts leaked on mobile but not desktop.** The mobile pass matched with `t===m || t.startsWith(m)` while the desktop pass used `includes`, so any label that did not begin with the marker was hidden on desktop and shown on mobile — and Facebook usually puts the author name first, as in "Julia Smith · Suggested for you". Mobile now uses `includes` like desktop, still bounded by the existing 40-character node cap that keeps it off post body text. Desktop and mobile now agree on every label tested.
- **Added the follow-suggestion phrases.** `Suggested accounts`, `People to follow`, `Accounts to follow` and `Pages to follow` were in no list, so they were shown on desktop as well. Checked against false positives: "Great suggestion from a friend", "I followed the recipe" and a bare "Follow" are all left alone.

### 8.8.0

- **Mobile view on desktop now actually reflows the page.** Previously it changed only what page JavaScript reads, so on a desktop browser it was close to a no-op on every site: measured on a live 1512px window, `matchMedia("(max-width:600px)")` returned `true` while the CSS `@media` behind it stayed `false` and the layout never moved. The three levers it pulled cannot work there — desktop browsers ignore `<meta viewport>` entirely, a userscript cannot change a navigation's UA header (every document request went out with the real desktop UA), and patching `window.matchMedia` does not affect CSS, which the layout engine evaluates itself. New `Reflow CSS` rewrites the site's own `@media` breakpoints in the CSSOM against the virtual phone width, covering `document`, `adoptedStyleSheets`, shadow roots, `@import`, and `media=""` attributes. Verified live: BBC 463 media rules rewritten and it renders its real mobile masthead and nav, Wikipedia 37, Hacker News 12, 0 blocked.
- **Fixed: `initVM` died silently at document-start.** When `documentElement` was not yet present, `applyVP()` threw on `appendChild` of the viewport meta and the top-level `run()` swallowed it. Everything after that line was lost — the MutationObserver, all four retry timers, the frame, and the `Alt+Shift+V` hotkey registration — and `vpLocked` was left stuck `true`, permanently blocking the retries meant to cover exactly this case. Hotkey registration now happens first, the DOM writes are guarded, and the retry schedule re-arms if the document root appears late.
- **Fixed: the viewport re-entrancy guard never worked.** `vpLocked` was set and cleared synchronously, but MutationObserver callbacks arrive as microtasks after that, so the guard was always `false` when checked — measured 18 full `applyVP` passes on one Wikipedia load. `applyVP` is now idempotent (it returns early when the meta is already correct) and is skipped entirely on desktop, where viewport meta has no effect.
- **Fixed: `matchMedia` missed unspaced queries.** The width tests used `\s*` but the feature tests were `includes("pointer: coarse")` with a literal space, so `(pointer:coarse)` — the form minified CSS and JS emit — fell through to the native result and answered `false` in Mobile mode. Queries are now parsed, not substring-matched.
- **Fixed: compound queries silently dropped their other terms.** `(min-width:768px) and (orientation:landscape)` was answered from the width alone. The spoof now rewrites only the terms it owns and hands the rest to the native engine, so unknown features stay correct — which also means `matchMedia` returns a real `MediaQueryList`, so `addEventListener` change events work. This removes the previous "returns a stub" limitation.
- **Frame contains fixed overlays.** The phone frame moved to the root element with a transform, making it the containing block for `position:fixed` descendants, so banners and sticky bars stay inside the phone instead of spanning the full window. `frameOnDesktop` now defaults on.

### 8.7.1

- **Fixed rails reappearing, compressed, after the feed is widened.** Rails were identified by comparing their position against the feed's _current_ rect — but widening the feed moves its edges, so on later passes the rails overlapped it and no longer qualified. They stayed visible and were then squeezed by the wider feed. The module was measuring against a value it had itself changed. Rails are now identified independently: a narrow `<aside>` that is neither inside the feed nor contains it, assigned left or right by which half of the viewport its midpoint falls in. Verified on a live feed across five consecutive passes with the feed widened to 900px throughout: both rails (216px and 312px) tagged on the first pass and still tagged on the fifth, none visible in any round, none left compressed.

### 8.7.0

- **Fixed the "works sometimes" behaviour on LinkedIn.** LinkedIn virtualises its feed, recycling DOM nodes for different posts as you scroll. The module marked each element it had examined with a permanent flag, so once a node had been checked it was skipped forever — and when LinkedIn reused that node for a _different_ post containing an ad, the ad was never examined. That is why filtering appeared to work on some posts and not others, and why results differed between sessions. Elements are now re-examined whenever their content changes, and an element that was hidden but no longer matches is released. Facebook already worked this way; LinkedIn did not.

### 8.6.7

- **Fixed the actual cause of "only the feed is missing" on LinkedIn.** The promoted-post sweep could hide the feed column itself. The column contains promoted posts, so it matches the markers, and whenever no child qualified as a tighter match the whole feed was tagged and hidden — leaving every surrounding element in place. The feed container and any ancestor of it are now excluded from the sweep outright. Verified live: feed visible at 900×1280 with its content, never tagged, both rails hidden, promoted posts hidden, none left in view.

### 8.6.6

- **LinkedIn feed detection rewritten against the live DOM, and tested there.** 8.6.3 through 8.6.5 each guessed at how to identify the feed column and each was wrong: by width (matched a page wrapper and squeezed the feed), then by counting post-shaped children (matched an empty skeleton placeholder with three children and zero text, while the real feed has only one such child). Measuring the live page showed the reliable signal is simply text: the feed is the **narrowest column at least 380px wide that contains real text**. Verified live end to end — the 552px feed is selected over both the 1128px wrapper and the empty skeleton, both rails are hidden, the feed stays visible with all its content, and widens 550 → 900px.

### 8.6.4

- **Fixed a regression in 8.6.3 that could hide or squeeze the LinkedIn feed itself.** Widening the search range to support wider layouts made it possible to select a page wrapper instead of the feed column, and the widening CSS then applied to the wrong element. The feed is now identified by structure rather than size — a column is only accepted if at least two of its direct children are post-shaped (tall, and nearly as wide as the column). If no such column is found, nothing is tagged and the module leaves the layout completely alone, which is the correct failure mode. Verified against wrapper, 552px column, 900px column and side-rail shapes.

### 8.6.3

- **Fixed: nothing hidden on wider LinkedIn layouts.** The feed column was located by a hard-coded 480–700px range, taken from the 552px column measured on one window size. On a wider window — or any layout where LinkedIn gives the feed more room — no column matched, so nothing was tagged and the rails, top bar and widening all silently did nothing. Detection is now relative to viewport width (380px up to 80% of the window, capped at 1400px) and picks the widest matching column. Verified across six layouts from 1024px to 2560px: the old range missed three of them, the new one finds all six.

### 8.6.2

- **Fixed: turning off `Promoted` and `Suggested` also disabled rail hiding and feed widening.** Those are independent features, but an early return sat between the stylesheet being installed and the sweep being wired — and the sweep is what tags the rails and feed column. So with both post filters off, the chrome settings silently did nothing. The chrome tagging now runs regardless; only the promoted-post scan is gated on having markers.

### 8.6.1

### 8.5.2

- **Fixed: promoted posts stayed visible while scrolling LinkedIn.** LinkedIn scrolls an inner container (`main#workspace`), not the window, so the module's `window` scroll listener never fired and sweeps fell back to the 1.5s timer — which you outscroll. Measured on the live feed: scrolling that container produced **0 window scroll events and 7 capture-phase events**. Both Facebook and LinkedIn now also listen in the capture phase on `document`, which catches scrolling from any container. The detection itself was never at fault: once a promoted post was in view, the existing sweep hid it correctly.

### 8.5.1

- **Fixed a hole in all three tightest-match scanners** (LinkedIn, the Facebook tile-grid pass, and the rotation fallback). Each skipped a matching element if one of its children also matched — correct, so a row is never hidden for one ad tile. But the child test only checked width and minimum height, while the main loop also enforces a maximum height and a viewport band. So an oversized or off-screen matching child would suppress its parent and then be rejected itself, and **neither was hidden**. Proven on a fixture: a 718px card containing a 2000px matching child was missed by the old logic and is caught by the new. A child now only suppresses its parent if it would itself be eligible.

### 8.5.0

- **Added LinkedIn.** Hides Promoted posts and, optionally, Suggested/recommended content in the feed. Toggle with `Alt+Shift+L`, the 💼 button, or the panel. LinkedIn has moved to fully hashed class names — `feed-shared-update-v2`, `data-urn` and the other long-standing selectors all match nothing now — so this module uses no selectors at all. It reads rendered text and hides the tightest post-sized element containing a Promoted label, the same approach that makes the rotation fallback honeypot-immune. Verified on a live feed: 5 promoted posts hidden with 69 genuine posts untouched. The two promoted units that survived 8.5.0 were traced to scroll detection, fixed in 8.5.2: LinkedIn scrolls an inner container so the window scroll listener never fired. The 8.5.1 eligibility fix was a separate real bug found along the way.

### 8.4.0

- **Added a markup-rotation safety net.** When the health check reports that sponsored labels are visible — meaning the normal selectors have stopped matching — a fallback engages that ignores markup entirely. It reads only _rendered_ text (position-aware, filtered by computed style and geometry) and hides the tightest bounded element containing a sponsored label. This matters because Facebook is documented to plant **hidden "Sponsored" honeypots inside ordinary posts** specifically to make naive text-matching blockers hide real content; reading rendered text rather than the DOM is immune to that by construction. It is a safety net, not a replacement: tested with every known selector renamed, it recovered 4 of 10 ad elements with **zero** of 20 real videos affected, in 20ms. Partial recovery with no collateral damage is the intended behaviour — it only runs when detection is already failing, so normal operation is unchanged.

### 8.3.0

- **Added `Seek past ads`, and a note on why you might turn it off.** When an ad has no working skip button the script seeks the player to the end. That is the most effective way to clear an unskippable ad, but it is also the exact signature YouTube's detection is described as looking for — an ad slot that loaded but never played, with an impossible timing profile. If you get repeated "Something went wrong" playback errors on videos with unskippable ads, switch **Seek past ads** off: skipping, muting and all feed/banner hiding keep working, and unskippable ads simply play muted instead of being jumped. On by default, because skipping ads is the point.

### 8.2.3

Verified on desktop Marketplace: 19 ads hidden, no sponsored label left visible, and all 48 real listings untouched. The reel machinery itself worked fine on mobile — video, container and skip target all resolve — it was simply gated out. Reels handling is now ungated (it already self-guards on the URL path).

### 8.2.1
